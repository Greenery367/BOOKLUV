🔍 성과 달성 핵심 요인 (Key Success Factors)
1. 연결 성공률 (1.4% → 100.00%)
* 트래픽 쉐이핑(Traffic Shaping): 유저 ID별 0.3초 순차 입장 전략을 통해 0.1 CPU가 감당할 수 있는 리듬으로 부하를 분산했습니다.
* Retry Storm 방지: 실패 시 무한 재접속을 시도하는 클라이언트 정책을 수정하여, 서버가 불필요한 에러 처리에 자원을 낭비하지 않도록 설계했습니다.

2. 연결 지연 시간 (14,620ms → 48.68ms)
* 직렬화 방식 혁신: 텍스트 기반 JSON 파싱을 제거하고 MessagePack 기반의 바이너리 읽기 방식을 채택하여 CPU 연산 시간을 획기적으로 단축했습니다.
* Payload 다이어트: 데이터 Key 값을 최소화(ex. message → m)하고 필수 필드 위주로 재설계하여 패킷 생성 및 전달 속도를 최적화했습니다.

3. 네트워크 트래픽 (11,100 MB → 19.2 MB)
* 99.8% 데이터 압축: JSON 형식을 바이너리로 변환하여 데이터 크기를 물리적 한계치까지 압축함으로써 네트워크 대역폭 점유율을 최소화했습니다.
* 중복 I/O 차단: 불필요한 브로드캐스트 트래픽을 제어하고 클라이언트와의 통신 빈도를 서버 가용량에 맞춰 재조정했습니다.

4. 서버 CPU 사용률 (9.82% → 0.05%)
* 연산 효율 200배 향상: 저사양 환경에서 가장 큰 부하를 주던 '문자열 파싱' 작업을 '바이너리 처리'로 전환하여 CPU 사이클 소모를 극적으로 줄였습니다.
* OS 커널 부하 경감: 수만 건의 재접속 요청을 차단함으로써 커널 수준에서 발생하는 불필요한 인터럽트 및 컨텍스트 스위칭을 제거했습니다.

## 1. 문제 정의
* **환경적 제약:** 0.1 CPU는 초당 수백 건의 JSON 파싱과 Handshake 요청을 동시에 처리하기에 절대적으로 부족한 자원임.
* **병목 현상:** 리소스 부족으로 응답이 늦어지자 클라이언트가 무한 재접속을 시도하는 **Retry Storm**이 발생, 서버가 '실패 응답'조차 못 하는 마비 상태에 빠짐.

## 2. 해결 전략 1: MessagePack을 이용한 데이터 경량화
* **바이너리 직렬화:** 텍스트 기반 JSON 대신 **MessagePack**을 도입하여 직렬화 비용 및 네트워크 페이로드 크기 최소화.
* **Payload 최적화:** 불필요한 필드를 제거하고 Key값을 단축하여 0.1 CPU가 처리해야 할 데이터 연산량 자체를 줄임.

## 3. 해결 전략 2: Retry Storm 방지를 위한 트래픽 쉐이핑
* **접속 정책 수립:** `Per-VU Iterations` 설정을 통해 실패 시 즉시 재접속을 차단하여 불필요한 트래픽 93% 제거.
* **Staggered Arrival:** 유저 ID별로 0.3초의 입장 지연을 부여하여 서버가 감당 가능한 리듬으로 트래픽을 분산 처리(Traffic Shaping).

## 4. 최종 결과 분석: 환경적 제약 극복
* **성능의 질적 변화:** 단순히 사양을 높여 해결한 것이 아니라, **단위 데이터당 소모되는 CPU 사이클을 줄임**으로써 0.1 CPU라는 물리적 한계 안으로 서비스를 밀어 넣는 데 성공함.
* **네트워크 효율:** 11GB의 트래픽을 19MB로 압축하며, 무료 호스팅 환경에서 발생할 수 있는 네트워크 초과 과금 및 대역폭 제한 문제를 원천 차단함.
